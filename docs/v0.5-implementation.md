# Working trip workspace: v0.5 implementation specification

Status: implementation baseline, 18 October 2026. Offline conflict policy, shared notes and personal lists confirmed by the user; storage sizing and operational retention remain implementation decisions. This specifies the first working implementation of the [workspace prototype](ux-direction.md), before a visual redesign. Production code and deployed data are unchanged. The rules below guide implementation; remaining technical choices must be measured and documented.

## Outcome and scope

One application supports desktop planning, mobile field viewing, shared editing by invited co-travelers, and a simple visitor view. Map and Species use the same trip/stop selection. Preserve the existing species methodology, imports, exports, map tools, stop editing, bulk time shifts, routes and observer-comment exports. Reuse production functions rather than shipping the prototype script as application code.

Do not add GPS tracks, a journal, new observation entry, public trip discovery, trip reuse by strangers, polygon areas or real-time automatic collaborative merging. Alternative plans may reference one dataset, but comparison tools and an active-plan workflow are deferred. Each trip has its own report connection; do not introduce a project/expedition hierarchy.

## Confirmed product decisions

1. Offline editing with revision checks and recovery copies (option 2). Authorized people can edit cached data offline. Online presence discourages overlap but is advisory, not a lock. Publish against the base cloud revision; never silently merge or overwrite a newer version.
2. Existing stop notes are shared itinerary content and visible in visitor view.
3. Account-owned life/region lists are personal; stop species of interest are shared trip content. Co-travelers may see different remaining-life targets while seeing the same itinerary. Initially use a per-trip reference to a personal region list rather than automatic geographical matching.

### Offline conflict recovery

Keep the base revision and a compact local plan snapshot separately from large cached source data. On reconnect, publish automatically only if the cloud still has that base revision. If the transaction is rejected because another revision exists, durably preserve the complete local plan as a named recovery copy before opening the latest cloud version. Show a persistent recovery notice with access to that copy and an export action. Keep recovery data until explicitly discarded; recovery creation/export must not require connectivity or a spare cloud trip slot.

Initial reconciliation is manual: inspect the recovery copy, open the current shared trip and reapply desired edits normally. Do not add a whole-trip overwrite shortcut or automatic field merging. Online overlapping edits, two tabs and one person's laptop/phone use the same rule. If the previous upload succeeded but its acknowledgement was lost, a stable commit ID identifies that success on retry rather than creating a false conflict. Serialize each device's uploads and retain edits made during an in-flight save for its next revision.

A locally created trip can be edited offline and published when connectivity returns; account access and capacity are checked at publication. A previously opened trip must expose whether the application shell, plan and selected analysis data are available offline. Browser storage is device storage, not a substitute for an acknowledged cloud save or exported backup.

Offline scope includes cached itinerary, notes, targets and geometry edits. Routes, place search, report refresh and new historical data require network access; keep existing results and mark invalidated results stale. Cached data availability must be explicit before departure, especially for species analysis. Map tiles remain a separate offline-coverage issue. The owner/editor permission matrix still applies; offline devices may retain changes after access revocation, but the backend must refuse to publish them.

## Data boundaries

Use Firebase Authentication, Firestore and Storage already present in the application, with IndexedDB for a device cache and recovery. No new backend platform is proposed. Exact document sizes, object partitioning and indexes must be validated with the existing large fixtures before committing the storage format.

| Record           | Authoritative content                                                                                                                                            | Change frequency and access                                                         |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Trip             | Stable ID, schema version, name, time zone, dataset revision reference, itinerary revision and report snapshot reference                                         | Small edits; visitors receive only the published view                               |
| Stops            | Stable UUID, explicit order, type, name, local date/time, duration in minutes, centre, radius in metres, shared targets and note according to the decision above | Frequent edits; same committed revision across itinerary and species views          |
| Routes           | Endpoint stop IDs and coordinate signatures, route profile, geometry, travel duration/distance and computation time                                              | Changed only for affected legs; geometry kept out of frequently cloned editor state |
| Dataset revision | Immutable imported EBD aggregates, location metadata and taxonomy version; separate lazy-loaded checklist/comment objects                                        | Uploaded once per import/replacement; reusable across the owner's alternative plans |
| Report snapshot  | Report ID, capture time, source endpoint coverage, checklist metadata, joined observations and global totals                                                     | Immutable successful refresh; retain known incomplete coverage                      |
| Personal list    | Account owner, kind, name, taxonomy version, taxon codes and update time                                                                                         | Private account data; never in anonymous trip responses                             |
| Access           | Owner UID, invited editor identities, public-view flag                                                                                                           | Owner-only changes; stored separately from public content                           |
| Editor presence  | Trip ID, account/session identity and last activity/expiry                                                                                                       | Advisory signed-in activity; never public, never authorizes writes                  |
| Device recovery  | Trip ID, base revision, pending plan snapshot, commit ID and time                                                                                                | Local, durable recovery; never silently replayed over a newer trip                  |

Large dataset storage must not inherit a public trip's permissions automatically. Visitors load a purpose-built itinerary/report projection, without personal lists, editor identities, raw historical checklists or observer comments. Editor analysis reads the source dataset through explicit access checks. A dataset referenced by two trips remains available while either needs it; deletion and access revocation must account for both references. Shared dataset bytes should be charged once to their owner; new size/slot accounting must be agreed before replacing the current 50 MiB archive allowance.

Use one explicit time zone per trip initially. Store planned wall-clock date/time in that zone and duration in minutes. Convert the legacy field named `durationMin` according to its actual hours convention at the migration boundary, once. Do not infer successful birding from a past date. Cross-time-zone scheduling is a known limitation of this first model and must be checked against the user's examples.

## Saving and consistency

1. Persist an accepted edit to a small IndexedDB recovery record before treating it as locally saved. Group continuous typing into one undo operation and debounce cloud commits; flush promptly on explicit completion and when switching trips or entering Preview, when online. Do not rely on tab-close network requests.
2. Commit small plan changes with a transaction checking current access and the base itinerary revision. Increment the revision on success. Bulk shifts are atomic. Avoid uploading or rewriting the EBD, comment corpus and unchanged route geometry.
3. Update the visitor view from the same committed plan revision. Use an explicit allowlist of public fields. Keep the previous complete visitor revision visible until the new one is ready; do not expose half-updated stops or a client-authored unsanitized archive. Choose an atomic small projection or a trusted publication operation after measuring plan size.
4. Show Saved only after cloud acknowledgement. Pending/failed saves remain visible to editors with retry and recovery export. Visitors have no save indicator. Saving never changes sharing permissions.
5. On reconnect, compare revisions before applying pending edits. If the base changed, preserve the recovery copy and open the latest cloud version; do not offer a casual overwrite of another editor's work. Provide an explicit recovery/export path.
6. Keep bounded session undo/redo for plan edits, including after an autosave; undo is a new valid edit. Persistent recovery checkpoints are separate from undo. Define checkpoint retention and deletion recovery before enabling destructive production changes; never retain a full dataset per keystroke.

This replaces manual browser-copy/cloud-copy management in the normal workflow. IndexedDB remains an implementation detail and a recovery mechanism. Export/import remains available for backups and old files.

## Ownership, sharing and editor presence

| Role           | View                       | Edit plan/report                                 | Share/delete | Personal analysis                                  |
| -------------- | -------------------------- | ------------------------------------------------ | ------------ | -------------------------------------------------- |
| Owner          | Yes                        | Online and offline; revision-checked publication | Yes          | Own lists                                          |
| Invited editor | Yes                        | Online and offline; revision-checked publication | No           | Own lists                                          |
| Visitor        | Published public view only | No                                               | No           | No private lists or historical analysis by default |

A private trip is visible to its owner and invited editors; an anonymous viewing URL works only when public viewing is enabled. Preview uses visitor content and layout but can show the editor's pending local plan with a clear unsynced indicator outside the visitor content. Friends see the latest cloud-published revision. Entering Preview retains pending local changes and does not require a connection.

Show recent online editor presence as a warning, without blocking offline edits or promising exclusive access. Presence expiration and tab closure have no effect on write authorization. Enforce permissions and revision checks in security rules or trusted backend code. Access revocation blocks later server reads and writes even if an offline device still has a cached editable copy. Preserve rejected device changes for local recovery/export; do not publish them through an alternate path. Already downloaded data cannot be recalled.

## Computation and invalidation

Source data and derived results stay distinct. Tag cached results with dataset/report revisions, relevant stop inputs and calculation version. Ignore stale asynchronous responses after switching trip, changing inputs or receiving a newer result. Do not deep-watch or clone the entire dataset on each edit.

| Change                       | Recompute/invalidate                                                                      | Preserve                                                        |
| ---------------------------- | ----------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| Name, note, stop targets     | Labels, target filters and published content as appropriate                               | Spatial membership, probabilities, routes                       |
| Stop centre                  | EBD/report spatial membership, stop statistics, trip predictions; incoming/outgoing route | Other stops' spatial results                                    |
| Stop radius                  | EBD/report spatial membership, stop statistics, trip predictions                          | Routes                                                          |
| Duration                     | Duration-adjusted trip predictions and day totals                                         | Spatial membership, route geometry                              |
| Date/time or bulk shift      | Day grouping, past/future display, ordering if chronological, affected route adjacency    | Spatial membership; unchanged endpoint route results            |
| Stop add/remove/reorder/type | Affected membership, birding participation, adjacency, day totals and predictions         | Unaffected cached source data                                   |
| Report refresh               | Report memberships, recorded totals and remaining-target filters                          | Historical EBD membership and routes                            |
| Life/region list change      | Personal filters and expected remaining counts                                            | Shared plan, spatial results and routes                         |
| EBD revision change          | Historical statistics, spatial index, probabilities and species layer                     | Report source observations, itinerary geometry and valid routes |

Preserve the original probability and expected-count definitions with reference tests before refactoring. Filtering a species table must not change the expected-count denominator. Full-trip unions deduplicate locations/checklists across overlapping stop areas. A source checklist's coordinates never move when a planned stop moves. Spatial matching includes report observations across report dates; do not restrict to the planned visit day. Report locations outside all stops remain visible and count toward full-trip results.

Use a reusable spatial index for candidate lookup followed by the same exact distance rule. Move expensive import, clustering and aggregation work into a worker when measurements justify it. Load aggregate data for planning, checklist details on demand, observer comments on explicit expansion/export, and only the visitor projection for visitors. Map features should not duplicate the full observation corpus.

## Report refresh

Use the existing proxy through one data-access module; UI components consume normalized snapshots, not endpoint-specific responses. Fetch checklist metadata, global taxa and required taxon details with bounded concurrency and reusable cached responses. Record which requests succeeded and which checklist details are missing. An incomplete snapshot may be usable when explicitly labelled; failed requests never become zero species.

Stage refreshed objects before changing the trip's snapshot reference. Publish the new reference only after the intended fetch stage finishes and completeness is recorded, with an access/revision check. Keep the previous snapshot if the refresh cannot produce a usable replacement. Refresh triggers the same plan-save/publication flow. Connecting or disconnecting changes only this application's connection, never eBird itself. Disconnect leaves the itinerary and source report untouched; decide snapshot retention with the recovery policy.

## Migration

Support current IndexedDB trips, current cloud archives and older imported files. Read legacy inline checklists and absent comment corpora without silently discarding them. Assign persistent stop IDs and normalize units at import/migration; retain unknown source content in the original backup when it cannot be represented.

Create the new format alongside the old data, validate stop counts/fields, source totals, lists, routes and report references, and mark migration complete only after the cloud commit succeeds. Leave the old trip/archive recoverable until verification. Migration must be repeatable after interruption without creating duplicates. Existing public archive URLs may expose data excluded by the new visitor model: moving to a sanitized view also requires retiring old anonymous archive access, with explicit tests. Previously downloaded copies cannot be removed.

First implement one complete path: migrate/open Oman, select/edit a stop, autosave, reload, switch Map/Species and open the visitor link. Then edit offline, reload offline, reconnect and verify automatic sync; repeat with a competing cloud edit and verify both versions survive. Add the other features behind the same data/save boundary rather than implementing parallel persistence paths.

## Validation and examples

Use small deterministic fixtures in unit/emulator/browser tests. Keep cached report responses for reproducible tests and a separate optional live API check. Existing commands include `npm test`, `npm run test:cloud:rules`, `npm run perf:standard`, `npm run perf:large-flow` and `npm run build`. Extend the tests while each behavior is implemented; do not wait until the UI is complete.

Oman already covers 63 stops over 21 days, overlapping areas, reports outside planned stops, incomplete report details, routes, targets and observer comments. Reference checks include Al Saadah Park's two checklists/27 taxa through 16 February, expected location total 15.0 and Booted Eagle cumulative estimate 83.2398%. Verify against the same fixture/cutoff and methodology rather than treating these as live report totals.

Use the existing measured EBD reference and scale 2–4 generated fixtures from [the performance guide](../tests/perf/README.md). Record import/open time, post-load heap, selection/edit latency, clustering time, downloaded bytes and bytes written per save. Establish measured budgets before optimization; desktop imports may be expensive, but mobile viewing must not require the full historical dataset. Map tile offline availability is separate from cached itinerary/report data.

Additional user examples are helpful but not required to start: one older saved trip/archive with life/region lists; a contrasting large EBD export if available; and a trip crossing time zones if that must work in v0.5. No credentials, account access or eBird write permission are needed for this specification.
